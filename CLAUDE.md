# Focus HQ

Browser-based cartoon 3D office (Three.js) visualising a swarm of Claude Code agents (Claude Agent SDK) that work GitHub issues (gh CLI) and open PRs. README.md is a short front page; each feature has its own page under `docs/` (`docs/goals.md`, `docs/qa.md`, `docs/configuration.md`…), and `docs/architecture.md` maps the code.

When you change a feature, update its page under `docs/`, not the README (add a page, and a link to it in the README's Docs list, only for a new topic).

## Commands

Focus uses pnpm (`corepack enable` provides the version in `package.json`'s `packageManager`); `pnpm install` hard-links packages from one store per machine, so a fresh worktree installs in seconds. Don't add a `package-lock.json`.

- `pnpm run typecheck`: run after every change; covers `server/`, `client/src/` and `shared/`. It runs `tsc`, then `@effect/language-service`'s diagnostics, which fail on a floating (un-yielded, un-run) Effect.
- `pnpm run lint`: run after every change; ESLint with type-aware typescript-eslint rules (floating and misused promises) over the same files, and no non-null assertions (`x!`) in `server/` and `shared/` outside tests: narrow instead (a check, `??`, or a type guard like `hasLeadWork`, which turns an `Agent` into a `LeadAgent` whose `lead` is there).
- `pnpm run demo`: fake GitHub + scripted agents (`FOCUS_DEMO_SPEED=3` speeds them up). Use it to check UI and 3D changes. To watch a workflow in a transporter room, message a demo lead "run a workflow" (`POST /api/agents/<leadId>/message`) once their turn is over.
- `pnpm run demo:start` (`--built` to serve a build, without hot reload), `demo:status`, `demo:stop`: the demo office as an agent should run it, in the background on a free port, outliving the Bash call that started it; `start` waits until it answers and prints its URL. Its projects and goal leads keep their ids across a restart. Use it instead of a hand-rolled `nohup npx tsx server/index.ts --demo &`, and stop only your own with `demo:stop` (never by port or process name).
- `pnpm run build`: Vite build of the client into `dist/`.
- `pnpm test`: vitest unit tests (`*.test.ts` next to the code they cover). `vitest.setup.ts` seeds the server's random choices (Math.random, and the ids `randomHex` rolls) before every test, so runs repeat exactly; a failing test prints its seed (`FOCUS_TEST_SEED`). Don't write a test that needs randomness to tell things apart (unique temp folders come from `fs.mkdtempSync`), and don't call a failure flaky and rerun it: rerun it on its printed seed. `pnpm run test:repeat` runs the suite 20 times on successive seeds, shuffled, to find tests that pass only by luck.
- `pnpm run crap`: optional; runs the unit tests with v8 coverage and prints each function's CRAP score (complexity² × (1 − coverage)³ + complexity) for `server/` and `shared/`: the riskiest, the spread, and with `--changed` what the branch touched that's over 30 (`docs/crap.md`).
- `pnpm run scorecard`: optional; runs the gate (timing each step), counts the fence (type assertions, non-null, `any`, suppressions), Effect's reach in the server, tests and CRAP, and the office's numbers from the ledger, then saves the result in `~/.focus/scorecards/` and marks what got better or worse since the last one (`docs/scorecard.md`). Run it on the base branch and then on yours (`--no-save`) to show a change's before and after.
- `pnpm run flow`: optional; splits every closed goal's lead time into states (the lead at work, reworking, waiting on its background work, QA, a merge or the captain) from its lead's transcript and the ledger, and prints p50/p85, the biggest wait and the quality guards (`docs/flow.md`). Run it with `--since` before and after a change meant to make goals faster.
- `pnpm run qa-catch`: optional, and it costs QA reviews (about $0.60 each); plants one known bug in each of 10 recently merged goal pull requests, in throwaway clones, runs the QA officer's own review on each and counts how many QA caught (`docs/qa-catch.md`). `--dry` plants them without reviewing.
- `pnpm run smoke`: Playwright smoke test of the splash screen against a demo office on a free port; screenshots land in `smoke-shots/`.
- `pnpm run ship`: rebuilds the decks modelled in Blender (`blender/*.py`) into `client/public/ship/*.glb` and saves a `.blend` of each in `blender/build/` to look round. It also bakes each deck's ambient occlusion in Cycles (`blender/bake.py`: a lightmap atlas on a second UV map, carried in the GLB as its materials' occlusion texture), on the GPU if there is one: about 15 s for the lot on an Apple M4, plus a minute or two the first time while Cycles compiles its GPU kernels. Needs Blender (on the PATH, in /Applications or Program Files, or `BLENDER`), but only to change the ship: the GLBs are committed, so the office runs without it. Commit the GLBs with the script change, or push the script change alone to a branch: CI's Ship workflow (`.github/workflows/ship.yml`) builds them on its CPU and commits them back to the branch a few minutes later, so pull before pushing again.
- `pnpm run perf`: optional; walks a busy demo office on the GPU in headless Chromium (bridge, into a holodeck's hall, into a briefing room, twice) and prints each step's frame times, main-thread time, shader programs linked and MB of textures sent to the GPU. Run it before and after a change you expect to cost or save frame time.
- `pnpm run zfight`: scans a demo office's 3D scene for z-fighting (faces from different meshes in the same plane, less than 0.002 apart) and exits non-zero listing each pair with a world position. It's an optional check, not a routine step: run it when you want to, for example when you suspect flickering coplanar faces in geometry built in code (the Blender decks rarely have them). The scan lives in `client/src/world/zfight.ts`; intentional overlaps go in the allowlist in `scripts/zfight.ts`, each with a reason.
- `pnpm run gaps`: the opposite scan: faces from different meshes facing each other 0.002 to 0.05 apart over more than about 50 cm², like a panel hovering off its wall or a chair's legs off the floor, and exits non-zero listing each pair. Gaps tucked inside something else, or behind a holodeck's skin, don't count. Optional too: run it after building or moving furniture and fittings. The scan lives in `client/src/world/gaps.ts`; gaps that are meant to be there go in the allowlist in `scripts/gaps.ts`, each with a reason. Fix a gap by burying one thing a little inside the other rather than lining their faces up exactly.

Unit tests cover the pure decision code (QA verdicts and badges, prompts). Keep new decisions (what happens next, can this merge) in small pure functions with a test next to them, and leave the I/O to the caller. Verify 3D/UI changes by running the demo and taking screenshots with Playwright. `window.focusHQ` exposes `{ state, world, player, ui }`, so a script can teleport (`ui.goTo(ui.places()[i])`, `ui.goToAgent(id)`) and open panels (`ui.openAgent(id)`, `ui.openBoard(projectId)`…; `ui.panels.isOpen` is a getter) without pointer lock. `state` is the server's mirror (`projects`, `agents` Map, `project(id)`), `world.root` is the scene group to traverse (`world` itself isn't), `player.teleport(feet, lookAt)`. The agents' `mcp__browser__evaluate` tool lists the same hooks (`FOCUS_HQ_HOOKS` in `browserTool.ts`).

## Reviewing a pull request

When you QA a pull request, run `pnpm run crap --changed origin/<its base branch>` and report it as a check named **CRAP (advisory)**: how many functions the PR touched, their total, and each one over 30. Never fail a PR on it alone. When the PR adds a function over 30, or makes one worse, say so in your summary with the way down (split it into small pure functions, or test it), and weigh it for a spot-check. Coverage from tests that run code without checking what it does doesn't count: call those tests out. `docs/crap.md` explains the score.

## Conventions

- Server and client share types through `shared/types/`, a file per feature (`agents.ts`, `goals.ts`, `qa.ts`, `events.ts`…) re-exported by its `index.ts`, so imports stay `from '…/shared/types'`: put a new type in its feature's file (a new feature gets a new file and a line in `index.ts`); server→client traffic is `ServerEvent`s over `/ws`, client→server is REST under `/api`.
- Agents never push or open PRs themselves; the manager does that after the session ends (`server/agents/manager/delivery.ts`). The one exception in timing is each goal's lead (`task: 'lead'`, `lead_<projectId>_<suffix>`, `desk: LEAD_DESK`, its team station in `lead.station`, up to `TEAM_STATIONS` per room): a long-lived session with every repo checked out side by side in its workspace (`lead_…/<repo>`), which asks the manager to push and open the PRs mid-session through its `mcp__office__ship` tool (`officeTool.ts`). Its system prompt never changes during the goal (Claude Code keeps a session's first one on resume), so anything that changes, like the branch and the workspace list, goes in messages. The pure decisions are in `server/agents/lead.ts`; the plan for goals is `docs/goals-plan.md`. A room's other agents sit at its `DESKS_PER_ROOM` (2) individual desks (`desks.ts` picks one, and never sends a lead or QA home to make room).
- The permanent crew (each room's ops officer at its Ops station, Number One in the ready room, and the chief engineer, whose retros draft issues from the frictions in the ledger's session digests, gathered by `server/agents/engineer.ts` into `data/retros`) are read-only Claude Code sessions built in `server/agents/claudeCrew.ts`: Read/Glob/Grep (plus WebSearch/WebFetch for Number One) and the office's own tools, `dontAsk`, no settings loaded. They draft; the manager files.
- Cloud agents (`agent.cloud`) run through the bundled CLI's headless `--cloud` mode (`extraArgs`), relayed in the same SDK message stream; `sessionId` is the cloud session's id. The CLI only starts a new one headlessly while Anthropic's server-side rollout allows it; when it refuses (`cloudRefused` in `cloud.ts`), the agent fails with `CLOUD_UNAVAILABLE` and isn't retried in a new session. They push their own `focus/…` branch and nothing else; the manager publishes the branch first and still opens the PR. Screenshots reach their laptop through image blocks in tool results (`screenshotFrame` in `render.ts`).
- Main engineering's climber is one crew member, Lt. Rhee (`climbingEngineer`, one record at `CLIMBER_ID`, a fresh session each climb), working agents with `task: 'climb'` (`docs/climber.md`): while the captain keeps climbing switched on, one at a time on the office's own repo, deskless, on a `focus/climb-` branch, with a brief from `server/agents/climb.ts` instead of an issue; their PR is titled from their final message's `# ` line and never auto-merges (`captainMerges` in `shared/mergeGate.ts`). The `Climbs` part (`manager/climbs.ts`) starts the next once it merges or closes.
- Each room's QA officer is an agent with `task: 'review'`: one record per room (`qa_<projectId>`, `desk: QA_DESK`) reused from review to review, run by the same runner as developers but with a JSON-schema report. Each goal has a reviewer of its own for its lead's PRs (`qa_<leadId>`, `reviewFor` set), seated at the goal's team station. QA never touches GitHub; the manager posts the report as a PR comment (`manager/reviews.ts`).
- Anything shell-like goes through `run()` in `server/util.ts` (execFile, no shell), and `gh` through `GhRunner` in `server/github/runner.ts`. The one exception is the manager's own preview commands, which `PreviewMachine` in `server/previewMachine.ts` runs through a shell on purpose (`&&`, `npm.cmd` on Windows, project CLIs), each in its own process group; `previews.ts` ties each process tree to the preview's `Scope`, so closing it runs the stop command and kills the tree.
- 3D: toon materials from `world/materials.ts`. Text surfaces (screens, signs, boards) use `flat()` so they're unlit, or a `Hologram` (`world/hologram.ts`) for a screen that floats free of any frame (the Kanban board, the team stations' screens and signs): navy glass a little see-through where it's dark, in a glowing outline (cyan, or its `tint`, like a team screen's in its room's tone), solid while you aim at it (`userData.aim`, called from `pick` in `main.ts`). Its mesh goes on `OVERLAY_LAYER`, so it's drawn over the outlines and what's behind it is behind its glass, lines and all; a `FloorGlow` lays its light on the floor under it (the board's). Room contents are built in room-local coordinates; walls and colliders are in world coordinates via `Builder`. Never put two faces from different meshes in the same plane: keep them at least 0.002 apart, or give one material `polygonOffset` when moving it would visibly change the look.
- The building's look (bulkhead palette, LCARS signs and screens, sliding doors) lives in `world/starship.ts`; every doorway gets sliding doors (a deck's `door` markers, and the holodecks' own, which `Builder.slidingDoors` adds since they lock). Sounds live in `sound.ts`: the console chirps, button presses, combadge alerts and transporter beam are CC0 clips from `client/public/sfx/` (credited in its `CREDITS.md`), each falling back to a synthesised version until they've loaded or if they fail to; doors, station tapping and the engine thrum are synthesised with Web Audio. The `AudioContext` starts, and the clips load, on the splash screen's click.
- The ship is built in Blender, a deck at a time (`ship` in `main.ts` loads them into the `Ship` that `World` builds): decks sit side by side in world space, not stacked. A Python script builds each deck (`blender/`); it's the source, so change the script, not the `.blend`. When a deck or team station module loads, its static meshes are merged by material within 6 m patches of floor (`mergeStatic` in `world/merge.ts`), to cut draw calls, and so are a holodeck room's furniture and each crew member's body, head and arms (toon materials that differ only in colour merge too, their colours moved into the vertices): whatever's used (`interactive`), a screen, accent or lamp stays a mesh of its own, and anything else code needs to find or change afterwards must be kept out (`keep`). `?merge=0` leaves the meshes as Blender made them; the gap and z-fighting scans use it to name what they find. Only the part of the ship the camera's in is drawn (`world/regions.ts`): the command deck, main engineering, the holodeck deck, or a briefing room (`World.reveal`, before each frame, and before a doorway draws its far side), so anything new goes in its region's group: the command deck's root, the engineering deck's root, the builder's group for the holodeck deck, its `halls` for the training halls (each project's holodeck, `world/hall.ts`, through its door's portal on the deck, a copy of the shell built in `blender/training_hall.py` with its floor painted in the project's colour as a pod's accents are in its station's), and the World's `briefingRooms` for the stations' rooms. `?cull=0` draws all of it; the scans use that too. The architecture comes from the deck's GLB; what moves or changes at runtime stays in code. Custom properties tell the browser the rest (`blender/kit.py` lists them, `world/deckExtras.ts` reads them): markers for colliders, doors, places, areas, crew seats and turbolift stops, what pressing E on something does, and surfaces it draws itself (LCARS, space, carpet, and screens the World keeps drawing, like mission control). The ship is the command deck (the bridge, where you come aboard, and the ready room and lounge with Number One), main engineering (deck 5, `blender/engineering_deck.py`: a gallery round a well with the warp core rising through it from a lower level you look down into but can't walk to, since the player keeps to one floor height; its core's 'warp-core' surfaces pulse in `world/warpCore.ts`, and its MSD is a screen drawn by `world/msd.ts`; the chief engineer sits there) and the holodeck deck, which is built of modules (`kit.module`) that `HolodeckDeck` puts together for however many holodecks there are: it's only the hallway: each holodeck's door in its wall (built in code, since it locks for a hidden project) is a doorway to its training hall, which stands out in the world where `layout.ts` puts it, and nothing stands behind the hallway's walls. A vacant holodeck's hall is bare, with the yellow grid; a hidden project's has nothing behind its locked doors. The turbolift (E on a car's panel, `stopAt` in `world/turbolift.ts`) rides between the decks' cars. A team station is built in Blender too (`blender/team_station.py`, two modules loaded through `loadTeamStation`, a copy of each per station): a holo-pod with a door in the holodeck and the goal's briefing room, which stands out in the world (`briefingRoomAt` in `layout.ts`); each station also has three transporter rooms where its lead's workflows run (`blender/transporter_room.py`, its own GLB, dressed by `world/transporterRoom.ts`), far out beyond main engineering (`transporterRoomAt`), each a region of its own that `World.reveal` draws only from inside it, so a feed of one reveals from its `camera.at` before rendering. Its seat markers say where the lead, helpers and reviewer sit (the lead and reviewer either side of where the captain stands, the helpers at two curved consoles round behind, each with a PADD), and the browser draws the lead's session, the station's sign and the goal board with the lead's note on its screens (`goalScreens.ts`, which also floats the sign over the door), paints its `accent` surfaces in the station's colour and lights its door's `lamp`s by how its goal room stands (`goalRoomState` in `goalRoom.ts`). The two doorways are a `Portal` (`world/portal.ts`): while their doors are open, `PortalView` draws the far side into a render target from the camera carried through the doorway (clipped at the far doorway), which the alcove behind the near one samples in screen space, and stepping into the alcove moves the player through (`Player.transport`), so both doorways (`doorway()` in the script) must match exactly. A shader that writes display colours has to turn them back to linear and end in `#include <colorspace_fragment>`, or it comes out too bright through a doorway. The player collides only with axis-aligned boxes, so walls and long things at an angle collide as a chain of small ones (`collide_path`, `collide_footprint`).
- Each frame is drawn by a `Frame` (`world/frame.ts`), both the screen's (`SceneRenderer`, which adds SMAA) and the far side of an open doorway (`PortalView`, only where the doorway is on the screen), so nothing changes as you step through: the scene into a target, outlines, and the overlay on top. Contact shading where surfaces meet, which keeps things looking like they stand on the floor rather than float, isn't drawn per frame: the decks have their ambient occlusion baked in (`occludedToon` in `materials.ts` multiplies it over all their light), and furniture built in code gets a soft contact shadow on the floor under it (`world/contactShadow.ts`: add whatever new stands on a floor to its room's `ContactShadows`, before anyone sits in it, or give it a `contactShadow` of its own). The screen's frame adds SMAA below a pixel ratio of 1.75 (on finer screens edges are left as they are). Everything costly is per pixel, so the picture adapts (`client/src/resolution.ts`): the pixel ratio drops a step at a time while frames run slow waiting on the GPU, and climbs back when they keep up (`?adapt=0` holds it). `?stats=1` shows frame time, pixel ratio, draw calls and the GPU, and logs it at the office: a sample a second, with GPU time per pass (`world/gpuTimer.ts`: a frame marks its passes with `gpuBegin`), and each hitch, in `~/.focus/frame-stats/` (`docs/performance.md`), so a run on another machine can be read here. Nothing should be compiled or sent to the GPU as you walk into a room: `world/warmUp.ts` compiles every material in the scene, drawn or not (the overlay's on its own layer, as its pass draws them, with no lights), and sends every image texture, whenever the world syncs; canvases are sent as they're drawn, a room's a few MB a frame as you near its door (`TextureFeed`, from `World.ahead`), and a station's screen is drawn only while it can be seen or you're nearing its door (`world/screenRedraw.ts`), its blinking cursor sending only its own cell (`world/texturePatch.ts`); a station's sign, goal board, chart and pod screen (`Display.update`) and a hall's Kanban board likewise, at most every 2 s. In a training hall only that hall is drawn (`World.reveal`). The overlay is `OVERLAY_LAYER` (speech bubbles): things without depth of their own, which the passes that read depth would draw across; they still hide behind what's in front of them. The outlines (`world/outline.ts`) are drawn from the depth buffer, not per material: a line wherever there's a step in depth of more than 3 cm or a fold sharper than 60°, so materials can't opt out. To keep something unlined, sit it within 3 cm of what it's on and meet it at gentle angles. The outlines treat every pixel with a stencil value as sky, so keep the stencil to the landscapes (which draw their own hull outlines) and the doorways' alcoves.
- Holodeck landscapes (`world/themes.ts`) are drawn through a stencil mask, so build them only with the `Kit` from `world/scenery.ts` (its materials carry the mask; with a plain `toon()` material, the object would turn up in whichever hall it physically overlaps). Keep landscape objects out of the hall's round footprint (`HALL.radius` round the middle of its floor): test with `Kit.clear` (`world/footprint.ts`, which also moves anything left inside out beyond its wall).
- Imports are extensionless (Vite + tsx both resolve them).

## Effect

`server/github/`, `server/previews.ts` and the agent manager (`server/agents/manager.ts`, its parts in `server/agents/manager/`, and its services in `services.ts`) run on [Effect](https://effect.website/); the rest of the server is still Promise-based and reaches them through adapters at the edge (`toProvider` in `server/github/service.ts`, the one `ManagedRuntime` each in `Previews` and `AgentManager`, whose public methods stay Promise-based or synchronous). An agent's work runs as a fiber in the manager's `FiberMap`, one per agent, so interrupting it (sending them home) stops their Claude Code session. `docs/effect-assessment.md` has the background and the migration path.

The manager is split by concern: `AgentManager` (`manager.ts`) is only the public API, each method handing over to a `Part` (`manager/core.ts`) in a file of its own under `server/agents/manager/` (seating, sessions, delivery, conflicts, leads, slices, goalTools, comms, reviews, triages, cloudMoves, ledger). The parts share one `Core`: the store and hub, the runtime, each agent's fiber (`runs`) and runtime state. A part reads like the manager did (`this.store`, `this.update`, `this.print`, `this.runFor` go to the core) and reaches another concern through it (`this.core.reviews.requestReview(…)`). Put new work in its concern's part; `manager.ts` only gains a line when the office needs a new public method. Parts are built in `AgentManager`'s constructor, not in `core.ts`, which imports them only as types (a value import would be circular).

- We're on **Effect v4** (`effect` is pinned exactly). Read `node_modules/effect/CLAUDE.md` and `node_modules/effect/ai-docs/` before writing Effect code, and don't write APIs from memory: `Context.Tag`, `Effect.Service`, `Effect.async`, `catchAll` and `either` are v3 names that don't exist here (`Context.Service`, `Effect.callback`, `Effect.catch`, `Effect.result`).
- Services are `Context.Service` classes; their implementations (live, demo) are Layers, usually a static `layer`. Tests provide fake Layers (and `TestClock` from `effect/testing` for time) rather than `vi.mock` or real sleeps.
- Errors are `Data.TaggedError` classes with a `message` getter that reads well in the UI and logs. Classify failures once, at the I/O boundary (`classify` in `server/github/runner.ts`); never fail with a bare string.
- Give a helper an explicit `Effect.Effect<A, E>` return type when it can return either `succeed` or `fail`; otherwise TypeScript infers a union of two Effects and later errors point nowhere near the cause.
- Style: `pipe` for one or two steps, `Effect.gen` for anything with control flow, `return yield* new SomeError(...)` to fail.
- Do side effects inside `Effect.sync`/`Effect.suspend` (or an `Effect.gen` body), never while *building* an Effect: a service method that pushes to an array before returning `Effect.succeed` runs at the wrong time.
- Resources that need cleaning up (processes, servers) are acquired with `Effect.acquireRelease` into a `Scope`; polling is `Effect.repeat` with a `Schedule`; deadlines are `Effect.timeout`/`timeoutOrElse`.
- Decode external JSON with Effect Schema. zod stays only at the Claude Agent SDK's tool boundary (`claudeCrew.ts`, `browserTool.ts`, `officeTool.ts`), which requires it.
