# Focus HQ

Browser-based cartoon 3D office (Three.js) visualising a swarm of Claude Code agents (Claude Agent SDK) that work GitHub issues (gh CLI) and open PRs. README.md is a short front page; each feature has its own page under `docs/` (`docs/goals.md`, `docs/qa.md`, `docs/configuration.md`…), and `docs/architecture.md` maps the code.

When you change a feature, update its page under `docs/`, not the README (add a page, and a link to it in the README's Docs list, only for a new topic).

## Commands

- `npm run typecheck`: run after every change; covers `server/`, `client/src/` and `shared/`. It runs `tsc`, then `@effect/language-service`'s diagnostics, which fail on a floating (un-yielded, un-run) Effect.
- `npm run lint`: run after every change; ESLint with type-aware typescript-eslint rules (floating and misused promises) over the same files.
- `npm run demo`: fake GitHub + scripted agents (`FOCUS_DEMO_SPEED=3` speeds them up). Use it to check UI and 3D changes.
- `npm run build`: Vite build of the client into `dist/`.
- `npm test`: vitest unit tests (`*.test.ts` next to the code they cover).
- `npm run smoke`: Playwright smoke test of the splash screen against a demo office on a free port; screenshots land in `smoke-shots/`.
- `npm run ship`: rebuilds the decks modelled in Blender (`blender/*.py`) into `client/public/ship/*.glb` and saves a `.blend` of each in `blender/build/` to look round. Needs Blender (on the PATH, in /Applications, or `BLENDER`). Commit the GLBs with the script change.
- `npm run zfight`: scans a demo office's 3D scene for z-fighting (faces from different meshes in the same plane, less than 0.002 apart) and exits non-zero listing each pair with a world position. It's an optional check, not a routine step: run it when you want to, for example when you suspect flickering coplanar faces in geometry built in code (the Blender decks rarely have them). The scan lives in `client/src/world/zfight.ts`; intentional overlaps go in the allowlist in `scripts/zfight.ts`, each with a reason.
- `npm run gaps`: the opposite scan: faces from different meshes facing each other 0.002 to 0.05 apart over more than about 50 cm², like a panel hovering off its wall or a chair's legs off the floor, and exits non-zero listing each pair. Gaps tucked inside something else, or behind a holodeck's skin, don't count. Optional too: run it after building or moving furniture and fittings. The scan lives in `client/src/world/gaps.ts`; gaps that are meant to be there go in the allowlist in `scripts/gaps.ts`, each with a reason. Fix a gap by burying one thing a little inside the other rather than lining their faces up exactly.

Unit tests cover the pure decision code (QA verdicts and badges, prompts). Keep new decisions (what happens next, can this merge) in small pure functions with a test next to them, and leave the I/O to the caller. Verify 3D/UI changes by running the demo and taking screenshots with Playwright. `window.focusHQ` exposes `{ state, world, player, ui }`, so a script can teleport (`ui.goTo(ui.places()[i])`, `ui.goToAgent(id)`) and open panels without pointer lock.

## Conventions

- Server and client share types through `shared/types.ts`; server→client traffic is `ServerEvent`s over `/ws`, client→server is REST under `/api`.
- Agents never push or open PRs themselves; `server/agents/manager.ts` does that after the session ends. The one exception in timing is each goal's lead (`task: 'lead'`, `lead_<projectId>_<suffix>`, `desk: LEAD_DESK`, its team station in `lead.station`, up to `TEAM_STATIONS` per room): a long-lived session with every repo checked out side by side in its workspace (`lead_…/<repo>`), which asks the manager to push and open the PRs mid-session through its `mcp__office__ship` tool (`officeTool.ts`). Its system prompt never changes during the goal (Claude Code keeps a session's first one on resume), so anything that changes, like the branch and the workspace list, goes in messages. The pure decisions are in `server/agents/lead.ts`; the plan for goals is `docs/goals-plan.md`. A room's other agents sit at its `DESKS_PER_ROOM` (2) individual desks (`desks.ts` picks one, and never sends a lead or QA home to make room).
- The permanent crew (each room's ops officer at the New issue stand, and Number One in the ready room) are read-only Claude Code sessions built in `server/agents/claudeCrew.ts`: Read/Glob/Grep (plus WebSearch/WebFetch for Number One) and the office's own tools, `dontAsk`, no settings loaded. They draft; the manager files.
- Cloud agents (`agent.cloud`) run through the bundled CLI's headless `--cloud` mode (`extraArgs`), relayed in the same SDK message stream; `sessionId` is the cloud session's id. The CLI only starts a new one headlessly while Anthropic's server-side rollout allows it; when it refuses (`cloudRefused` in `cloud.ts`), the agent fails with `CLOUD_UNAVAILABLE` and isn't retried in a new session. They push their own `focus/…` branch and nothing else; the manager publishes the branch first and still opens the PR. Screenshots reach their laptop through image blocks in tool results (`screenshotFrame` in `render.ts`).
- Each room's QA officer is an agent with `task: 'review'`: one record per room (`qa_<projectId>`, `desk: QA_DESK`) reused from review to review, run by the same runner as developers but with a JSON-schema report. Each goal has a reviewer of its own for its lead's PRs (`qa_<leadId>`, `reviewFor` set), seated at the goal's team station. QA never touches GitHub; `manager.ts` posts the report as a PR comment.
- Anything shell-like goes through `run()` in `server/util.ts` (execFile, no shell), and `gh` through `GhRunner` in `server/github/runner.ts`. The one exception is the manager's own preview commands, which `PreviewMachine` in `server/previewMachine.ts` runs through a shell on purpose (`&&`, `npm.cmd` on Windows, project CLIs), each in its own process group; `previews.ts` ties each process tree to the preview's `Scope`, so closing it runs the stop command and kills the tree.
- 3D: toon materials from `world/materials.ts`. Text surfaces (screens, signs, boards) use `flat()` so they're unlit. Room contents are built in room-local coordinates; walls and colliders are in world coordinates via `Builder`. Never put two faces from different meshes in the same plane: keep them at least 0.002 apart, or give one material `polygonOffset` when moving it would visibly change the look.
- The building's look (bulkhead palette, LCARS signs and screens, sliding doors) lives in `world/starship.ts`; every doorway gets sliding doors (a deck's `door` markers, and the holodecks' own, which `Builder.slidingDoors` adds since they lock). Sounds live in `sound.ts`: the console chirps, button presses, combadge alerts and transporter beam are CC0 clips from `client/public/sfx/` (credited in its `CREDITS.md`), each falling back to a synthesised version until they've loaded or if they fail to; doors, station tapping and the engine thrum are synthesised with Web Audio. The `AudioContext` starts, and the clips load, on the splash screen's click.
- The ship is built in Blender, a deck at a time (`ship` in `main.ts` loads them into the `Ship` that `World` builds): decks sit side by side in world space, not stacked. A Python script builds each deck (`blender/`); it's the source, so change the script, not the `.blend`. When a deck or team station module loads, its static meshes are merged by material within 6 m patches of floor (`mergeStatic` in `world/merge.ts`), to cut draw calls: whatever's used (`interactive`), a screen, accent or lamp stays a mesh of its own, and anything else code needs to find or change afterwards must be kept out (`keep`), as the briefing table is. `?merge=0` leaves the meshes as Blender made them; the gap and z-fighting scans use it to name what they find. Only the part of the ship the camera's in is drawn (`world/regions.ts`): the command deck, the holodeck deck, or a briefing room (`World.reveal`, before each frame, and before a doorway draws its far side), so anything new goes in its region's group: the command deck's root, the builder's group for the holodeck deck, and the World's `briefingRooms` for the stations' rooms. `?cull=0` draws all of it; the scans use that too. The architecture comes from the deck's GLB; what moves or changes at runtime stays in code. Custom properties tell the browser the rest (`blender/kit.py` lists them, `world/deckExtras.ts` reads them): markers for colliders, doors, places, areas, crew seats and turbolift stops, what pressing E on something does, and surfaces it draws itself (LCARS, space, carpet, and screens the World keeps drawing, like mission control). The ship is the command deck (the bridge, where you come aboard, and the ready room and lounge with Number One) and the holodeck deck, which is built of modules (`kit.module`) that `HolodeckDeck` puts together for however many holodecks there are: the holodecks' contents, landscapes and doors (built in code, since they lock) stand where `layout.ts` puts them, so its walls keep to its sizes. The turbolift (E on a car's panel, `stopAt` in `world/turbolift.ts`) rides between the decks' cars. A team station is built in Blender too (`blender/team_station.py`, two modules loaded through `loadTeamStation`, a copy of each per station): a holo-pod with a door in the holodeck and the goal's briefing room, which stands out in the world (`briefingRoomAt` in `layout.ts`). Its seat markers say where the lead, helpers and reviewer sit round the table (with PADDs: there's no console in front of them), and the browser draws the lead's session, the station's sign and the goal board with the lead's note on its screens (`goalScreens.ts`, which also floats the sign over the door), paints its `accent` surfaces in the station's colour and lights its door's `lamp`s by how its goal room stands (`goalRoomState` in `goalRoom.ts`). The two doorways are a `Portal` (`world/portal.ts`): while their doors are open, `PortalView` draws the far side into a render target from the camera carried through the doorway (clipped at the far doorway), which the alcove behind the near one samples in screen space, and stepping into the alcove moves the player through (`Player.transport`), so both doorways (`doorway()` in the script) must match exactly. A shader that writes display colours has to turn them back to linear and end in `#include <colorspace_fragment>`, or it comes out too bright through a doorway. The player collides only with axis-aligned boxes, so walls and long things at an angle collide as a chain of small ones (`collide_path`, `collide_footprint`).
- Each frame is drawn by a `Frame` (`world/frame.ts`), both the screen's (`SceneRenderer`, which adds SMAA) and the far side of an open doorway (`PortalView`, only where the doorway is on the screen), so nothing changes as you step through: the scene into a target, N8AO's screen-space ambient occlusion for contact shading where surfaces meet (`?ao=0` leaves it out), outlines, and the overlay on top. The overlay is `OVERLAY_LAYER` (speech bubbles): things without depth of their own, which the passes that read depth would draw across; they still hide behind what's in front of them. The outlines (`world/outline.ts`) are drawn from the depth buffer, not per material: a line wherever there's a step in depth of more than 3 cm or a fold sharper than 60°, so materials can't opt out. To keep something unlined, sit it within 3 cm of what it's on and meet it at gentle angles. Both passes treat every pixel with a stencil value as sky, so keep the stencil to the landscapes (which draw their own hull outlines) and the doorways' alcoves.
- Room landscapes (`world/themes.ts`) are drawn through a stencil mask, so build them only with the `Kit` from `world/scenery.ts` (its materials carry the mask; with a plain `toon()` material, the object would turn up in whichever room or hallway it physically overlaps). Keep landscape objects out of the room footprint (|x| < ROOM_DEPTH / 2, |z| < ROOM_WIDTH / 2 in room-local coordinates).
- Imports are extensionless (Vite + tsx both resolve them).

## Effect

`server/github/`, `server/previews.ts` and the agent manager (`server/agents/manager.ts`, with its services in `services.ts`) run on [Effect](https://effect.website/); the rest of the server is still Promise-based and reaches them through adapters at the edge (`toProvider` in `server/github/service.ts`, the one `ManagedRuntime` each in `Previews` and `AgentManager`, whose public methods stay Promise-based or synchronous). An agent's work runs as a fiber in the manager's `FiberMap`, one per agent, so interrupting it (sending them home) stops their Claude Code session. `docs/effect-assessment.md` has the background and the migration path.

- We're on **Effect v4** (`effect` is pinned exactly). Read `node_modules/effect/CLAUDE.md` and `node_modules/effect/ai-docs/` before writing Effect code, and don't write APIs from memory: `Context.Tag`, `Effect.Service`, `Effect.async`, `catchAll` and `either` are v3 names that don't exist here (`Context.Service`, `Effect.callback`, `Effect.catch`, `Effect.result`).
- Services are `Context.Service` classes; their implementations (live, demo) are Layers, usually a static `layer`. Tests provide fake Layers (and `TestClock` from `effect/testing` for time) rather than `vi.mock` or real sleeps.
- Errors are `Data.TaggedError` classes with a `message` getter that reads well in the UI and logs. Classify failures once, at the I/O boundary (`classify` in `server/github/runner.ts`); never fail with a bare string.
- Give a helper an explicit `Effect.Effect<A, E>` return type when it can return either `succeed` or `fail`; otherwise TypeScript infers a union of two Effects and later errors point nowhere near the cause.
- Style: `pipe` for one or two steps, `Effect.gen` for anything with control flow, `return yield* new SomeError(...)` to fail.
- Do side effects inside `Effect.sync`/`Effect.suspend` (or an `Effect.gen` body), never while *building* an Effect: a service method that pushes to an array before returning `Effect.succeed` runs at the wrong time.
- Resources that need cleaning up (processes, servers) are acquired with `Effect.acquireRelease` into a `Scope`; polling is `Effect.repeat` with a `Schedule`; deadlines are `Effect.timeout`/`timeoutOrElse`.
- Decode external JSON with Effect Schema. zod stays only at the Claude Agent SDK's tool boundary (`claudeCrew.ts`, `browserTool.ts`, `officeTool.ts`), which requires it.
