# The chief engineer's retro

A plugin (`FOCUS_PLUGINS=retro`, [plugins](../../docs/plugins.md)): the chief engineer looks back over the frictions found in the agents' sessions and drafts an issue for each that keeps coming back, for you to accept (it's filed) or reject. It needs no other plugin.

In main engineering (deck 5: take the turbolift, or teleport to 🔧 Engineering), <kbd>E</kbd> on Lt. Brennan's station opens his panel (the master systems table beside it [reviews the ledger](../../docs/ledger.md#reviewing-it)). The retro adds a card to its overview (whether one is under way or waiting on you, and the most widespread open frictions) and a **Retro** view of its own, whose readout says `LIVE` while one runs, or how many drafts wait. There **Start a retro** looks back over the last 14 days (or however many you choose, up to 60). While one runs or waits on you, Brennan's bubble and the last line on his station's screen say how it stands (`Retro: 2 drafts waiting`); otherwise he's keeping the ship running.

Each agent session is digested into the ledger as it ends, from code alone, by the core (see [Session digests](../../docs/ledger.md#session-digests)). A retro then:

1. **Reads the sessions no one has read yet.** Before it starts, the panel says how many there are in the window and roughly what reading them costs (about $0.025 a session of Claude usage, from the bake-off; sessions read before aren't read again). The engineer reads their trimmed text (`frictions.ts`) with Claude Opus 5.5, about a hundred sessions a batch, with a 20-second pause between batches so a retro doesn't take all the office's usage at once, and writes what each held to the ledger (`session-frictions`). A session whose transcript isn't on this machine (a cloud session's) is noted as missing and left be.
2. **Code groups the frictions** (`frictionGroups` in `shared/ledger.ts`): by kind and signature, counting each session once, leaving out any group you've already decided on. A group that came up in **three or more sessions** is a pattern worth an issue; one seen in two goes under **To watch**. With nothing at three, the retro says so and stops there: no model is asked.
3. **The engineer drafts issues.** The plugin writes the groups (with their quoted moments), the ledger's report card and your earlier decisions, and the closed goals into `~/.focus/retros/<time>/`. The engineer, a read-only Claude Code session like [Number One](../../docs/number-one.md), reads only that folder and drafts an issue for each group worth fixing (or one for a few that are plainly the same trouble), in the form of #159: what keeps happening and what it costs, **What to build** (the cheapest fix that would do: a check the office runs before a rule in a prompt) and **Done when**, with its kind of fix and the number to watch. It may leave out a group whose moments aren't the office's doing. Code checks each draft rests on real groups, one draft per group, and adds the **Evidence** section itself from the quoted moments (`parseDrafts` in `retro.ts`), so what's cited is what was found.
4. **You decide.** Each draft shows on the panel with the issue as it would be filed. **Accept and file** files it in the repository picked beside it (one of the project's own: the office refuses any other; the last one you picked is remembered); **Reject** doesn't. Either way the decision goes in the ledger (`retro-decision`) with the frictions' signatures, so later retros leave them be, and the report card can tell whether an accepted fix stopped them recurring (see [Did the retro's fixes work?](../../docs/ledger.md#did-the-retros-fixes-work)). The Retro view lists those fixes and how each did. A draft can be decided on once: a second click while the first is still filing is refused. The **Filed** toast shows whichever project you're looking at (the plugin's toasts carry no project).

The engineer changes nothing and files nothing itself. The latest retro is kept in the plugin's slot of `state.json` (`plugins.retro`; one under way when Focus stops ends as interrupted as the plugin starts again), and each one's folder keeps its evidence and `retro.json`. A retro saved before the retro was a plugin moves into its slot as the office starts, if one ever ran (`server/plugins/migrate.ts`).

## Without it

The engineering station keeps its overview and its **Ledger** view (the report card, the open frictions, and **Digest them** for older sessions), and Brennan keeps the ship running. The ledger keeps its vocabulary: the session frictions and retro decisions already in it still show in the ledger review, the report card's retro fixes, the scorecard and the climber's briefs. But no new frictions are read, so the open frictions, the scorecard's patterns and fixes that stopped their friction, and the climber's evidence stay as the ledger last had them.

## Where it lives

- `server.ts`: the plugin: the chief engineer, scripted in the demo, and its routes under `/api/plugins/retro` (`POST /preview {days}`, `/start {days}`, `/stop`, `/decide {id, accept, projectId?, repo?}`).
- `engineer.ts`: `ChiefEngineer`: reads the unread spans through `host.transcript`, writes what it found with `host.record`, groups and gathers the evidence, runs one retro at a time in the plugin's state, and files an accepted draft with `host.fileIssue`.
- `retro.ts`: pure: what the engineer reads (the frictions, the ledger, goals), the prompt, the schema, and the check that every draft rests on real groups, with the evidence added by code.
- `frictions.ts`: what the reader reads of each session's span, the batches, prompt and schema, and the check that every quote is in the span.
- `claudeEngineer.ts`, `demoEngineer.ts`: the live engineer (read-only Claude Code sessions, on the captain's model through `host.settings`) and the demo's scripted one.
- `shared.ts`: the retro's state (`Retro`, `RetroDraft`), how it picks up after a restart, and what Brennan says at the station.
- `client.ts`, `view.ts`: the card, the Retro view, and the station's line (`EngineeringPart.station`).
