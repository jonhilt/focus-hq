# Goals and their leads

Each goal has a lead of its own: your own Claude Code session for that goal, which you talk to like any Claude Code session. A project has any number of goals: a goal doesn't need a team station (a goal started while goals took one keeps its seat).

- **Their workspace:** every repo of the project, checked out side by side on the goal's branch, so a change that runs through the API, the web app and the admin app is just one piece of work. They branch from there as they like, and their checkouts stay as they are for the whole goal. A goal starts titled with your first words; Haiku's short title replaces them unless the lead has retitled it meanwhile.
- **How they work:** their prompt says what you want of them and how Ops works, and leaves how to run a slice to them. What you want: shape the goal first (talk it through briefly: what, why, what done looks like, no spec); prove risky assumptions early; bring real things back for judgement calls (running code, a screenshot, a mockup, a diagram of the code), and otherwise make a sensible call and say so; and keep pull requests reviewable. Ops doesn't make them keep a checklist, name a slice or keep the brief short: the chart is drawn from what they actually do.
- **Their workflows:** with autonomy on ask, the lead asks you once before running a workflow, and approving it lets that workflow's own agents run their commands without asking, for that run, rather than every one of them raising the lead's hand. A workflow runs on after the lead's turn ends, and the lead keeps listening meanwhile, so a message you send while it runs reaches them straight away rather than after the workflow ends. So does anything else they have running in the background, a shell or a monitor: Claude Code keeps the session going until it ends anyway. It keeps listening through the turn Claude Code takes for the last task's result, and stops once that's over, or a minute on if no turn comes: stopping as the task ended left that turn nobody to ask, and Claude Code cancelled each tool it needed approval for with "The user doesn't want to take this action right now". A workflow Ops has seen start and not end holds it open too, whatever Claude Code lists. So does a message sent just as a turn ends, which Claude Code takes in a turn of its own: Ops waits for that turn rather than closing on it.
- **Their pull requests:** they push their own branches and open pull requests with `gh`, as many as the work needs, in whichever repos it touches: a draft while it's in progress, marked ready when it's ready for review. Ops never pushes or opens one for them. Ops claims it as the goal's when the board next refreshes: an open pull request whose branch exactly one lead's checkout of its repo has been on (that checkout's own HEAD reflog), never a base branch, and never one a lead or developer already holds (`server/agents/manager/goalPrs.ts`). It joins the goal's pull requests with a `pr` ledger line and a line on their station, once however often the board refreshes, and stays claimed through a restart. Marking it ready (`gh pr ready`, or opening it ready) is how they ask for review: where the project sends pull requests to QA itself, Ops sends it once the board sees it ready and QA hasn't looked at it, and they hear the verdict as they would a shipped one's. A draft isn't sent. The first time Ops sees one of the goal's pull requests ready, it writes a `pr-ready` ledger line: when it went out, which [flow](../plugins/flow/README.md) and the captain's log read as a ship. As their turn ends, each ready pull request of theirs with a verdict goes back to QA, whose precheck re-tests it once if they pushed to it since and leaves the verdict standing if not: several pushes in a turn get one re-test. Git refuses two pushes of theirs, saying how to carry on: to a base branch, and to a branch whose pull request already merged (a squash merge leaves its commits off the base, so a new pull request from it would carry them again). The refusal is a pre-push hook: every local session's git runs Ops' hooks (`server/agents/pushGuard.ts`, set through its environment so a repo's own `core.hooksPath` can't replace them), each of which hands on to the repo's own hook, and a command with `--no-verify` or its own `core.hooksPath` is refused before it runs. Which branches is written for each lead as their turn starts and as a pull request of theirs merges.
- **Reviews on GitHub:** a review on one of the goal's open pull requests, by anyone (you on GitHub, a teammate, a review bot), reaches the lead as a note, with what it said and its comments on the code, once each however often the board refreshes, and none half told after a restart (`goalPrsInvariants.test.ts`). The board's own pull request list brings the reviews, so finding one costs nothing more; only a new one has its comments on the code read. Plain comments on a pull request aren't sent: Ops and QA post theirs as plain comments from the same account, so a review is what tells someone's word on the work apart. A review that only comments and says nothing (the wrapper of a reply) is heard but not told. Like every note it doesn't wake the lead: tell them what to do about it, or let a plugin wake them (the chief of staff doesn't, for a review).
- **Hearing back:** only you start a lead's next turn. What Ops and QA have for them (QA's verdict on a pull request, pass or fail, their slice landing, Ops merging a base into their pull request) is a note: kept in their run journal, so a restart doesn't lose it, and heard with the next message they get, ahead of it, whether that comes mid-turn or starts their next one. A note never wakes them, and never carries a turn on as it ends. A QA fail says so in a toast: the lead waits on you (or, mid-turn, hears it with their next message, and if the turn ends without one, the lead waits on you then). None says so when a plugin's message for it picks the lead up, brings it into their turn, or is held for your plan's usage limit. A fail's note doesn't say when to fix it: the message it comes with does. Waking them for news was core's until it wiped the turn you hadn't read yet, and with it what the lead had asked you; a plugin can still wake them for a note (it hears of each one), and [the chief of staff](../plugins/chief-of-staff/README.md) does, for a QA fail it sends back and a slice that's landed, unless you owe the lead an answer. You merge their pull requests (they don't merge by themselves). Once every pull request of the slice has merged or closed, the goal moves on to its next slice there and then: they hear so, and their checkouts stay as they are, for them to start what's next on a fresh branch from the base (a push to a branch whose pull request merged is refused, since a squash merge leaves its commits off the base).
- **The goal's brief:** the lead keeps the goal's brief in `./brief.md`, at the root of their workspace beside the repos (in no repo, so never committed), with Claude Code's own file tools: a `#` title, then what done looks like, what the slices taught, ideas for next and the loose threads, each under a heading of its own. Ops only reads it (`server/agents/briefFile.ts`): as the lead's Write or Edit of it finishes, and as each of their turns starts and ends, so an edit made some other way shows by the turn's end (`manager.test.ts`, *reads the lead's brief*). It reads the headings loosely, and one missing only means that part doesn't show. Its title becomes the goal's. The lead hears the whole brief again, with your first words on the goal, once their conversation is compacted, by Ops or by Claude Code itself (a `SessionStart` hook), and when they have to start afresh. A lead from before the brief hears once, as their next turn starts, to write it from the note they kept. It replaced a note tool (`mcp__office__note`) whose fields, line limits and contact ids were bookkeeping a lead had to learn: a file is what Claude Code already knows how to keep. It goes with the goal when it closes, and a reopened goal's lead writes it back if it's gone.
- **The goal's chart:** Ops keeps a waypoint for each slice as the lead works, with what it set out to do, a change of what done looks like, QA's verdicts and spot-checks, and QA's screenshots copied into the goal's own files, since the review and the board's entry are both gone once the pull request lands. A re-test's spot-checks replace the last round's, keeping your tick on any it picks again. **Contacts** are the loose threads a lead noticed on the way, listed in their brief rather than chased: each bullet there is a contact, open while the brief lists it and cleared once the lead takes it off (Ops numbers them itself, so the lead never needs an id). One spun off as a goal of its own is the new goal's, and stays closed while the brief still lists it; its lead hears to take it off. An idea for next spun off stays off the chart the same way. Lessons are the whole goal's, in the brief, rather than each waypoint's. A goal's course is laid out from its id, so it always meanders the same way. The rules the chart is held to are measured in `client/src/ui/legibility.ts` (no label over another, a mark or a line, labels kept apart, no leaders crossing), and its tests hold a busy voyage to them with each waypoint in focus at several zooms.
- **Their context:** a goal can run for a long time in one conversation, and every step of a turn reads the whole of it again, so a big one is the costliest part of a goal (over 30 days, three quarters of what leads' own conversations cost came from steps that read more than 200k tokens). So before a lead's next turn, once their conversation has grown past the threshold in Focus's settings (**Compact a lead's conversation from**, 0 to switch it off), Ops compacts it first, telling Claude Code what to keep: between turns, so never in the middle of one, and never in a cloud session. If it can't, it carries on as it is and doesn't try again in that conversation. Tested on a real lead's 627k conversation, the compacted one (a few thousand tokens) answered a blind-graded quiz on the goal (what you asked for, your pushback, the decisions, each PR and what became of it, what's next) almost as well as the full one, 15 points to 16: what it lost were details like file and line numbers, which the code and GitHub still hold. Claude Code still compacts by itself when a context fills up. Leads are also told to hand broad exploration to subagents and keep only their conclusions.
- **How hard they think:** changing it costs a little, since the prompt cache starts over.
- **One per goal:** their record lasts as long as the goal, from slice to slice. Their instructions say who they are and how they work, and stay the same for the whole goal (Claude Code keeps a session's first system prompt when it resumes); where their repos are, and on which branch, comes in messages. Other leads may be working in the same repos at the same time, each on their own branches.
- **Showing you things:** the lead can put a visual on their station's big screen (`mcp__office__show`). Up close, the page runs sandboxed in an origin of its own, so its scripts can't reach Focus. They stay with the goal when it closes, with the questions you answered and what you picked, and reopening the goal puts them back on its screen. They're kept for good, even after the goal drops off the end of the room's log: they're often the best record of why something was built the way it was. `GET /api/goals/archive` (`?project=<id>` for one room) lists every goal the ledger saw close, with its artifacts and questions.
- **Diagrams of their code:** with the Architecture map plugin on, a lead shows how the code fits together with `mcp__office__map` and a state or flow chart with `mcp__office__statechart`, each drawn in one house style ([cartography](../plugins/cartography/README.md)); anything else goes up with `mcp__office__show`. Ops once had a model tool of its own that drew a structure diagram, a sequence diagram and the data at each step on one screen: it was removed because that much on one screen couldn't be read.
- **Asking you with pictures:** for a question best answered by looking, the lead asks it with options (`mcp__office__ask`), and your pick goes to the lead as a message from you. Any message you send them while a question's open settles it as answered in chat, with what you said kept beside it: the lead reads your message and acts on it, and Ops doesn't guess which option you meant.
- **Asking you with Claude Code's own questions:** a lead can ask with AskUserQuestion too (workers and QA can't: they work on their own). Each question goes up as one asked with `mcp__office__ask` does, on the station's screen and in Comms, each option's preview (self-contained HTML) its page, or a page of what the option says when it has none (`server/agents/questions.ts`). It's up only while the lead's turn waits on it: your pick, or whatever you write to the lead meanwhile, goes straight back into that turn as the answer. Several questions go up one after another, and the lead hears every answer together. If the turn ends first (the lead was stopped, or Focus restarted), the question comes down; the lead asks again if it still matters.
- **Ending a goal:** when what done looks like is met, or a slice lands and nothing worthwhile is left, the lead says so (`mcp__office__propose_close`), and you close it, or carry on talking. Closing never throws work away: uncommitted changes are committed as a WIP snapshot on the goal's branch before its checkouts go (and if that fails, the goal stays open). A goal can't close while its slice is shipping (so its pull requests stay with the goal), nothing ships once a close has started, and if Focus stops part way through a close it finishes the close when it starts again, rather than the lead picking up a goal whose work is half committed. It asks first if that leaves work only in the clone Ops keeps (a snapshot, commits never pushed, a branch that never reached GitHub), leaves pull requests open with no lead, or closes a goal that shipped nothing; a checkout git can't look at counts as having changes. A closed goal keeps what it taught you, the branch each repo was left on and every slice's pull requests. **Reopen** brings the same lead back, however many goals are under way, with every repo on the goal's branch as it was left (the WIP snapshot at its tip), and picks their conversation back up.
- **Goals in line:** a new goal always starts; nothing goes in line any more (`manager.test.ts`, *starts any number of goals in a project*). Goals left in line from when four team stations capped a project's goals never start by themselves: you start each one, and it starts there and then. Rejected: keeping the cap. A goal's work happens in its checkouts and its lead's conversation, not at a booth, so a booth was the only thing a fifth goal lacked.

Leads don't take one of the holodeck's individual desks or count towards its agent limit. They do count towards **Agents working at once** while they work: a message to a lead (or any agent) that has finished its turn waits for a free slot like anyone starting work.

## Why it's built this way

From Anthropic's guidance when goals were designed (prompting guides, *Harness design for long-running application development*, the compaction docs):

- A 1M window doesn't remove the need for context management: long runs get summarised, so what must survive (the goal's brief) lives outside the conversation.
- Anthropic's own harness moved from context resets with handoff files to plain compaction once models could hold a multi-hour build. What stayed useful was a short "what done looks like" agreed per chunk, not up-front specs.
- Compaction works best when the harness chooses the moment and says what to keep.
- The doer and the judge stay separate (QA).
- "Don't stop to report" prompting is for unattended agents; a lead tells the captain and stops.
- On `resume`, Claude Code keeps the first system prompt until the next compaction or a new session, so anything that changes goes to a lead as a message.

## The system recap

A pull request of the goal's can carry a **system recap**, which the lead puts on it with `mcp__office__recap`, after Kent C. Dodds' [visual recap](https://github.com/kentcdodds/kcd-skills): the primitives (the system's building blocks) it touches, each one **composes** (used as it is: wiring, call sites), **extends** (its behaviour or contract changed) or **adds** (a new one), the invariants it could break, a system map and a change flow (`server/agents/recap.ts`). The slice's rollup is its riskiest primitive's. It's there so you review the system first and read only the diffs that matter: an extended primitive's, and an added one's as design. Reading every diff was where your time went.

- **It covers every file the pull request changes.** Ops refuses one while any file in the pull request's diff is under none of its primitives' paths, and tells the lead which (`recapProblems`; `recap.test.ts`, and `manager.test.ts` for the tool). A recap that leaves files out would hide them from the one review you do.
- **It goes into the pull request:** a marked block in its description, its map and flow in mermaid, which GitHub draws. Sending it again puts the recap as it is now in place of that block, leaving the rest of the description as it was (`withRecap`).
- **And onto the lead's station screen,** as `system-recap-<number>`, so Comms shows its picture with the lead's turn. A picture that won't go up never holds the recap back.
- **Its map's arrows are checked against the code.** An arrow between two primitives is solid when a file of one imports a file of the other, either way round, and dashed when Ops found no import, with a key saying so (`recapImports.ts`). Dashed isn't refused: the browser calling the server over HTTP is a true arrow with no import behind it. Only JavaScript and TypeScript's relative imports are read, up to a few hundred files a primitive.
- The lead names the primitives itself, the same from one pull request to the next, and picks the pull request's [lane](merging.md#lanes-how-a-goals-leads-slice-merges), which the recap shows: never lower than its rollup allows. With no recap, a pull request is in Ask.

## No slice journal

A goal's slices have no journal of their own. Once leads opened their own pull requests, nothing of a slice is left for Ops to finish after a restart: the lead pushes and opens them, and the board's next refresh claims any it hadn't yet (as Focus starts). Where the slice is (its number, its pull requests, those landed) is kept with the lead in the store, and what happened to it is in the ledger (`pr`, `pr-ready`, `merged`, `closed`, `goal-closed`), which the captain's log reads. The journal it had (`~/.focus/runs/slices/`) was dropped rather than cut down: it recorded only when the first slice started and each pull request landing, which the ledger already had, and Ops never read it back. Its files from before are left on disk, unread.
