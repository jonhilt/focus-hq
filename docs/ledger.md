# The ledger

`~/.focus/ledger.jsonl` is the ship's log of how work went, one JSON line per event, appended and never rewritten: each QA verdict (with its commit, round and checks), each PR merged or closed (by whom, and QA's badge on it at that moment, so a merge without a QA pass shows), merge conflicts (cleanly merged by the office, settled by the repo's rules for union and generated files (`auto`), or an agent had to resolve them, with the files that conflicted so the retro can see which keep colliding: see [agents](agents.md)), checks sent back, triage decisions, each goal as it closes (uncapped, unlike the 30 goals `state.json` keeps), and a digest of each agent session as it ends (below). It outlives the reviews, agents and transcripts it's about: `state.json` drops a review when its PR merges and an agent when they go home, and Claude Code deletes transcripts after 30 days unless told otherwise. The engineering station's screen shows the last 30 days of it summed up (`reportCard` in `shared/ledger.ts`), and the [chief engineer's retro](retro.md) reads it too.

## Reviewing it

In main engineering (deck 5), <kbd>E</kbd> on the master systems table opens the ledger for review (`ui/ledgerPanel.ts`, its rules in `shared/ledgerReview.ts`; the office serves the window at `GET /api/ledger?days=`). It changes nothing: the [retro](retro.md), at Lt. Brennan's station, is where anything gets decided, and each panel links to the other.

- **The log:** the last 7, 14, 30 or 90 days, the newest first and grouped by day, each event as one line: `focus #236 · 2 of 7 checks failed · fail 2`, `focus #199 · by the captain · without a QA pass (QA stale)`, `focus #233 · an agent resolved them · 2 files`. Filter by project, and by kind (QA, merged, conflicts, goals, retro, sessions, frictions, each with its count). Sessions and frictions are most of the ledger, so they start hidden: they show in each trace anyway. The log shows its newest 400 lines.
- **The trace:** pick a line about a pull request to follow it in order, from the sessions that worked on it through its QA rounds, conflicts and triage to its merge, with the frictions found in each session quoted under it, and totals for QA fails, conflicts, sessions (their minutes and cost) and wasted calls. Its goal's name traces the whole goal: every pull request it opened in the window, its sessions, and its closing. A friction picked on the engineering panel (its bars of open frictions) opens the review on that friction's trace: every session it came up in, each quoting the moment, and any retro decision on it, with totals for the sessions, how many times it came up, the pull requests they worked on, and what those sessions cost and wasted.
- **On the wall:** the MSD beside the table shows the ledger next to the ship (`world/msd.ts`): the report card, the [scorecard](scorecard.md) when it's put up from the engineering panel, or once you pick one, the trace, with its totals and latest steps big enough to read from the gallery. It stays up after you close the panel, until you pick another or **Clear the MSD**.

## A proper log

- **Numbered lines.** Each line starts with the format's version (`"v":2`) and carries a sequence number (`seq`), one more than the line before.
- **One writer.** `LedgerLog` (`server/ledgerLog.ts`) appends each line and flushes it to disk (fsync) before the office carries on. A lock file beside it (`ledger.jsonl.lock`, holding the office's process id) keeps a second office on the same data folder from writing too: that one reads the ledger, keeps its own new lines in memory, and says so on the report card (as a note, not as damage). A lock left by an office that's gone is taken over.
- **Checked whole on load** (`checkLedger`):
  - a last line cut short (Focus stopped mid-write) is dropped and the file trimmed;
  - damage in the middle (a line that doesn't read, numbers missing, repeated or going back) is never skipped quietly: the office copies the file aside (`ledger.jsonl.damaged-<time>`, once: the same damage found on a later start points at the copy already made), says what's wrong at the top of the report card (**⚠ Ledger damaged**) and in its log, and carries on numbering from the highest line it read;
  - lines from the first format (before numbering) are numbered and the file rewritten once, the old one kept as `ledger.jsonl.v1-<time>`.

## Session digests

When an agent's session ends, the office digests what's new in its Claude Code transcript into a `session-digest` line (`server/agents/sessionDigest.ts`), from code alone: no model reads it as it ends. Its frictions are read later, at retro time (below).

- **When:** a developer or conflicts agent as they go home; QA as each verdict is in (the room's QA officer is reused from review to review); a lead as each slice lands, and as the goal closes.
- **What:** how long it ran, its tool calls, the calls that failed and those a guard, hook or permission check refused, failed calls run again unchanged, the wasted calls (failed plus run again: running the tests again after an edit isn't waste), the captain's messages and how many were nudges ("continue", "go", "ship it"), the office's messages, compactions, what it cost (the session's running total, less what its last digest counted), and the QA fails and conflicts on its pull requests so far.
- **Never twice:** each digest covers the transcript from the line after the last digest of that session to its end, and is keyed by the session and that last line. Calling it again with nothing new does nothing. A cloud session's transcript isn't on this machine, so it isn't digested.

- **Frictions, read at retro time** (`server/agents/frictions.ts`): when the captain starts a retro, the chief engineer reads each span in the window no one has read yet: a trimmed version of it (each message to the agent, the captain's in full with what the agent had just said, each failed call with its error, the agent's own words, and the ledger's lines on its PRs, about 10k tokens at most). Claude Opus 5.5 reads them about a hundred at a time, finds the moments where the office, its tools, the environment or the way of working got in the way, and gives each a kind from a fixed list (`FRICTION_KINDS` in `shared/ledger.ts`: demo-env, guard-block, shell, tool-refused, conflicts, qa-rerun, captain-correction, captain-nudge, missing-dependency, flaky-check, other) and a short signature, reusing the signatures already in the ledger so the same trouble groups together. Every friction is quoted, and code drops any quote that isn't in that span's text word for word. What it found in each span (none included) goes in the ledger as a `session-frictions` line, so no span is read twice. It only finds and quotes: it doesn't judge the work, rank anything or give verdicts.
- **Why Opus, not Haiku per session:** digests were first read by Haiku as each session ended. A bake-off on 9 Oct over the same 76 sessions found both cost about the same per session (Haiku's calls carry Claude Code's overhead each time) and found about as many frictions, but Haiku gave the same trouble different words (86 signatures to Opus's 36: merge conflicts split three ways, so the groups a retro counts fell apart), and missed some Opus found. Digests Haiku read keep their frictions, and count like the rest.
- **Older sessions:** the engineering station's panel counts the agents' transcripts on this machine that have no digest (from before digests began) and offers **Digest them** (from code alone, so it costs no Claude usage; their frictions are read at the next retro). The office digests them two at a time in the background, each dated when its session ended and marked `backfilled`; the agent is long gone, so its kind and project come from the transcript's folder, a QA session's PR from its request, and its cost from Claude Code's own running total when the transcript has one.

The report card shares the digests' cost and wasted calls out over the PRs merged in the window: **Per merge: $… · … wasted tool calls**.

## Did the retro's fixes work?

Each retro draft the captain accepts goes in the ledger with its frictions' signatures and the issue it was filed as (see [the retro](retro.md)). When a pull request merges, the office notes the issues it closed (`closes` on the `merged` line: the board's links, and the issue its developer was given), so the report card can tell when a fix landed. For each accepted fix (`fixEffects` in `shared/ledger.ts`) it counts the sessions its frictions came up in, out of the sessions digested: in the 14 days before the captain accepted it, and since it landed. It then says the fix is **waiting for its fix** (no merge has closed the issue yet), **too early to tell** (fewer than 5 sessions digested since), **stopped it** (its frictions haven't come up since), **fewer** (they come up in a smaller share of sessions than before), or **still recurring**. The report card sums them up (**Retro fixes: … accepted · … landed · … stopped it**), and the engineering panel's Retro view lists each with its before and after.
