# Plugins

The office's core is what anyone who adds a project needs: rooms and boards, goal leads, developers, QA, delivery and the ship itself. Anything beyond that is a plugin, switched on by name. Without a plugin, the office has no trace of it: no crew member, no card, no route, no saved state in use.

## Switching plugins on

`FOCUS_PLUGINS` lists the plugins to switch on, comma-separated, in the order they start:

```sh
FOCUS_PLUGINS=scorecard,climber pnpm start
```

- **A bare name** is a folder under the office's own `plugins/`, like `climber`.
- **A path** (anything with a slash, relative to where the office starts) is a plugin folder anywhere, like `../my-plugins/auditor`.
- **`all`** is every folder under the office's own `plugins/`, so `FOCUS_PLUGINS=all` switches the lot on (and `all,../my-plugins/auditor` one more besides).

A fresh office has none switched on. The demo office (`pnpm run demo`, `demo:start`) has them all unless `FOCUS_PLUGINS` says otherwise (`FOCUS_PLUGINS= pnpm run demo` for one with none, or a list to check a feature with and without it). The scripts that start a demo office of their own (smoke, perf, flows, the gap and z-fighting scans, through `startDemo` in `tools/demoOffice.ts`) always switch every plugin on, whatever `FOCUS_PLUGINS` the caller has (an agent inherits the office's), so none of them quietly loses a feature; the theme shots are taken from a demo office already running.

A plugin that can't be found, or doesn't load, is left out with a line in the office's log saying why. A typo never keeps the office from starting. `info.plugins` in the snapshot lists the plugins that did start.

A plugin's saved state stays in `state.json` while it's switched off, so switching it back on picks up where it was. Nothing of it runs meanwhile, not even its hold on pull requests only the captain merges, so the office warns as it starts when there's saved state for a plugin that isn't switched on.

Its `pnpm run flow` and `pnpm run before-after` scripts work whether it's switched on or not, and `pnpm run flow` shows [QA's catch rate](qa-catch.md) among its guards, read through the plugin API.

Adair, the ship's first officer, across the captain's desk in the ready room: a read-only chat about any project's code or the ship (<kbd>E</kbd> on them, or <kbd>1</kbd> anywhere aboard), with voice mode, a toast when a reply lands while you're elsewhere, and [calls](../plugins/number-one/calls.md) hands-free that start goals on your spoken yes. Without it nobody sits across the desk. Voice mode stays the core's kit (dictation and Kokoro, which the narrator shares): Number One brings their own voice to it.
- [The chief engineer's retro](../plugins/retro/README.md) (`retro`): Lt. Brennan reads the frictions in the agents' sessions and drafts an issue for each that keeps coming back, for the captain to accept (it's filed) or reject. Its card and Retro view are on the engineering station, and while one runs or waits on the captain, Brennan says so at his station. The ledger's frictions and retro decisions stay the core's vocabulary: without the plugin they're still read and shown, but no new ones are written.
- [The scorecard](../plugins/scorecard/README.md) (`scorecard`): main engineering's scorecards of the office's own repo, on the engineering station and the MSD. The `pnpm run scorecard` and `pnpm run crap` scripts live in it too, and work whether it's switched on or not.
- [Cartography](../plugins/cartography/README.md) (`cartography`): each project's architecture map, from the model its repos keep in `.focus/cartography.yaml` and the imports their code makes: on the engineering station's **Maps** view, each view drawn with numbered arrows and said in sentences, the whole map as a dependency matrix, and how it changes (hotspots and change coupling from git).
- [Briefings](../plugins/briefings/README.md) (`briefings`): a lead's animated explainer of a concept on their station's screen (`mcp__office__explain`), narrated in their voice up close. Switched on per project.
- [Your plan's usage](../plugins/usage/README.md) (`usage`): main engineering's readout of your Claude plan's usage, read from Claude Code's structured `/usage` every few minutes: a pill on the HUD, a block across the top of the engineering overview (a bar per limit, how the office signs in, and what each agent signs in with), and its gauges on the MSD. Without it nothing reads `/usage`; carrying on with your API key when the plan's limit is reached stays the core's, and the plugin reads where it stands through `host.signIn` and `signInChanged`.
- [Astrometrics](../plugins/astrometrics/README.md) (`astrometrics`): the office's state machines (a crew member's run, what follows a turn, a goal's slices, QA's review), drawn from their code on a screen in the holodeck, with where the project's runs of each are now lit; <kbd>E</kbd> on it opens them up close, a tab for each, where you can follow a run's trail through its machine. Switched on per project.
- [The captain's log](../plugins/captains-log/README.md) (`captains-log`): every journal the office keeps (each crew member's run, each pull request's review, each goal's slices) and the ledger on one timeline, newest first, with what happened while you were away and filters, on <kbd>J</kbd> anywhere aboard. It reads the journals through `host.journals`. Without it, <kbd>J</kbd> does nothing and isn't in the legend.
- [The chief of staff](../plugins/chief-of-staff/README.md) (`chief-of-staff`), in shadow mode: as a goal's lead ends a turn, it judges where the turn would go (carry on, a card for the captain, interrupt the captain, back to the lead) with Haiku and the captain's standing orders, and writes the verdict in the ledger (`cos-verdict`), acting on none of it. Switched on per project. Without it, no verdicts are written.
- [The climber](../plugins/climber/README.md) (`climber`): main engineering's crew member, who fixes the scorecard's worst gap in the office's own repo, one pull request at a time. It requires the scorecard plugin: switched on without it, it's left out, saying why.

## Plugins that need each other

A plugin that can't work without another says so: `requires: ['scorecard']` on its `FocusPlugin`. The office starts every plugin after the ones it requires, whatever order `FOCUS_PLUGINS` lists them in, and leaves out a plugin whose requirement isn't switched on, saying why in its log (`it requires scorecard, which isn't switched on (add it to FOCUS_PLUGINS)`). The plugins that require a left-out plugin are left out in turn, and so are plugins that require each other round a loop. The plugins left out, and why, are in `Plugins.leftOut`.

A required plugin lends what it shares through `provides`, returned from its `start` (the scorecard provides main's scorecards: `history` and `noise`). The plugin that requires it asks the host: `host.uses<ScorecardService>('scorecard')`, typed with the providing plugin's own interface, imported from its `api.ts`. Asking for a plugin it didn't require throws.

| Climber | Scorecard | What happens |
| --- | --- | --- |
| on | on | both start, the scorecard first, and the climber's briefs read main's scorecards through it |
| off | on | the scorecard alone: it needs nothing |
| on | off | the climber is left out, saying why: its routes, card and briefs aren't there, and its saved state waits |

The scorecard provides how to read a number too (`direction`: whether it's moved past its wobble; `formatValue`: how it's written), so the climber's pure rules take them from what it provides rather than from its code.

A plugin that others require can publish an `api.ts`: the one file of it another plugin may import, as `plugin-api/` is the one way into the core. The scorecard's (`plugins/scorecard/api.ts`) lends its types (`ScorecardService`, `Scorecard`…) and, for the climber's replay script (`pnpm run climb:replay`), which runs without a host, the saved scorecards (`SavedScorecards`, `scorecardsDir`) and how it words a change (`direction`, `formatValue`, `render`). Anything else of the scorecard it can change without the climber noticing.

## Switched on per project

`FOCUS_PLUGINS` switches a plugin on for the office. A plugin that works per project, like cartography, also has to be switched on for each project it should work on: a switch in the project's settings (the manager's **Projects** tab, under **Plugins**), off until you switch it on. The project keeps the list (`Project.plugins`, `shared/projectPlugins.ts`), and the office:

- shows the switch only for the plugins switched on in the office whose `client.ts` declares `project` (a `label` and an `about`);
- keeps a plugin's lead tools out of the offices of goals in projects it's off for, and its holodeck screens out of their halls (a plugin that stands something in a hall with `ship` checks `pluginOn` itself: the ship's built again whenever a project's plugins change);
- tells the plugins when a project's settings change (`projectChanged`), so one switched on starts its work there at once, and one switched off drops what it had;
- answers `host.on(projectId)` for the plugin to ask itself.

Plugins about the office as a whole (the scorecard, the climber) don't declare `project`, and take no notice of the switch. The demo switches every plugin on for its two projects.

## What a plugin adds

A plugin is a folder with a `server.ts` that default-exports a `FocusPlugin` (`server/plugins/contract.ts`): an `id` and a `start(host)` that returns what it adds. Every part is optional:

- **Briefs.** A brief is work the plugin hands an agent in place of an issue. The agent has task `brief`, and `agent.brief` says whose brief it is (plugin and kind), with a label and icon for the name tag, the panels and the Tricorder. Like an issue, a brief starts a new branch from the repo's default one and ends in a pull request the office opens. The plugin's `BriefSpec` supplies:
  - the system prompt's assignment and what the final message must be;
  - the first message (`brief`, an Effect that may read GitHub);
  - the pull request's title and body from the final message (no `Closes #…` is added, since there's no issue);
  - whether they work away from the room's desks (`away`: `AWAY_DESK`, outside the room's limit);
  - what the demo office's scripted stand-in writes up (`demo`).
- **Routes.** Each `PluginRoute` is mounted under `/api/plugins/<id>`. A handler's return value goes back as JSON, and a throw becomes a 400 with its message.
- **Hooks.**
  - `boardRefreshed`: a project's board was read from GitHub again (about once a minute), a moment to look at how its work stands.
  - `prOpened`: the office opened or updated the pull request of an agent on one of its briefs.
  - `prClosed`: any pull request merged or closed, a goal's too (once the goal has heard).
  - `turn`: an agent's turn started or ended, any agent's (the flow plugin keeps leads). A turn cut short still ends, and a turn can start and end more than once in what looks like one (carrying on, a retry, a new session), so take each as how the agent stands now. `end` comes before the office acts on how the turn went, so the agent's status still says `working`: go by the phase.
  - `modelShown`: a goal's lead drew a model of how the code works with their `model` tool: its id and title, the model as the office's check left it, the page drawn of it, and its picture. Cartography keeps them for the architecture space.
  - `ledgerRecorded`: a line went in the ship's log, any kind. It's heard as it's written, before the office has acted on what it says (a goal's pull request merging is logged before the goal knows), so read the office afresh a moment later rather than straight away.
  - `machineStepped`: one of the office's state machines stepped: a journal took a fact, so a run of it (an agent's, a goal's, a pull request's review) may be in another state. Read `host.machines()` for where it is now. Astrometrics redraws its screens.
  - `projectChanged`: a project's settings changed, a plugin switched on or off for it, say.
  - `captainMerges`: whether only the captain merges a pull request, whatever QA and auto-merge say. It goes by branch, since a pull request outlives its agent.
  - `signInChanged`: the office's new sessions moved onto your API key (your plan's usage limit was reached), or back onto your plan, with where it stands now (`host.signIn()`'s answer). The usage plugin redraws its readout on it.
- **Lead tools.** `leadTools`: tools added to the office of every goal lead whose project the plugin's switched on for beside ship, note and show, as `mcp__office__<name>`. Each has a `name` (lowercase, digits and underscores; one the office's own tools have, or another plugin's already took, is left out), a `description` the lead reads, an `input` of zod fields, and `run(lead, input)`, which answers in words, or with `{ text, images }` to give the lead JPEGs to look at too (a throw is said back as the tool failing). `lead` is a `LeadToolContext`: the lead's agent, their `checkouts` of the goal's repos as they stand in their workspace, `show(page)`, which puts a page on their station's screen as their show tool does, and `showFrames(page, { at, clip })`, which does the same and takes a picture of the page at each moment in `at` too, clipped to `clip`: the page jumps to each through its own `window.kitSeek(at)`, and its `window.kitSeen(jpeg)` (given the picture as base64 JPEG) says what it sees in it, handed back as each frame's `seen` for the plugin to narrow (the explain tool's player says how flat its stage is and where its labels landed, to tell the lead what looks wrong). `demo({ folders, again })`, if it has one, is the input the demo office's scripted lead calls it with (`again` when the captain asked for more on it): the briefings plugin's explainer goes up in the demo that way. The cartography plugin's `map` tool is the first, and the briefings plugin's `explain` another.

A hook that throws is logged and skipped, so one plugin's bug never stops the office's loops.

## What the office lends a plugin

`start` gets a `PluginHost`. What it reads of the office is a copy of its own (`server/plugins/lend.ts`): the agents, projects, settings, snapshot and ledger it asks for, and the agents and ledger lines its hooks hear of. It can keep and change them, but that never changes the office's, or what another plugin hears. The API types them read-only too (`Agent`, `LeadAgent`, `Project` and `LedgerEvent` from `plugin-api/` are `Readonly`), so writing to one is a compile error. The ledger is copied a line at a time as it grows, not whole on every call.

- **State.** `host.state(fresh)` is the plugin's own slot in `state.json` (`plugins.<id>`). `set` saves it and sends it to every browser as a `plugin` event; the snapshot carries each plugin's state in `plugins`. A field the plugin adds later starts at its `fresh()` value. With `{ saved: false }` it's kept in memory only, for state the plugin reads again as the office starts (the scorecards, read from disk). A plugin can keep both on its id: the browser gets them side by side, so their keys mustn't meet (Number One saves its `chat`, but not what it's reading this moment, nor the call, which change too often or mean nothing after a restart). Nothing is saved until it's first set, so an office that never used a plugin has nothing of it waiting.
- **Seating.** `host.seat` hands one of its briefs to an agent: someone new, or `crew` when it's always the same person, who keeps one record (and terminal) from brief to brief. `host.forget` drops what the office kept of their last session, so the next starts afresh.
- **Reading the office.** Its projects, an agent by id or every agent (`agents`), an agent's last terminal lines (`recentLines`), a file a goal's lead put on their screen (`artifact(leadId, file)`: `<id>.html`, or its picture `<id>.jpg`), the ledger, an agent session's Claude Code transcript by its session id (`transcript`: none for a cloud session's, and the scripted stand-ins in the demo, its pretend leads' and its older sessions'), the captain's settings (`settings`: the model a read-only session runs on, say), how the office's sessions sign in to Claude (`signIn`: `mode` is your plan, your API key, or your plan with the key behind it; `onKey` whether new sessions are on the key now; and what the key has spent of its budget while your plan's limit is reached), and the office's own repo (`ownRepo`, from its checkout's remote; none in the demo).
- **The office's state machines.** `machines()` gives each of them as data (`server/agents/machines.ts`: its states, nested as they are, and its transitions with their events and named guards, read from its XState definition), and where every run of each is now: each agent's run and what followed their last turn, each goal's slices, each review on the boards. `machinePath(machine, key)` is a run's path through one, read from its journal: the state it started in, then each state it moved into and when, its last 60 steps.
- **The journals.** `journals(since)` is every journal the office wrote to since `since` (by their files' times), each with its `key` and every fact it holds, oldest first: each agent's run journal (`runs`, by agent id), each pull request's review journal (`reviews`, by `owner/repo#12`) and each goal's slice journal (`slices`, by its lead's id). What a journal adds up to is the core's own machine's, re-exported pure from `plugin-api/server.ts` (`evolveReview`, `evolveSlice`, their `EMPTY_…` and `factLine` for a run's fact in words), so a plugin tells the facts as the office does. The captain's log reads them.
- **Writing the ledger.** `record` writes a line in the ship's log and sends the new report card. Every plugin hears it on `ledgerRecorded`, the one writing it too.
- **Filing an issue.** `fileIssue` files one on GitHub and puts it on the project's board straight away. Only in one of that project's own repos: the office refuses any other.
- **Files and checkouts.** `dataDir()` is the plugin's own folder for what it keeps (`<data dir>/plugins/<id>`); its scripts find the same folder with `pluginDataDir(id)`. Both take `movedFrom`, a folder the office kept in its data dir before the plugin was one, to move what's in it across (the scorecard's `scorecards/`, the retro's `retros/`). `checkout(repo)` checks out a repo's default branch as it is on GitHub now, in a folder of the plugin's own, and says where: only one of the office's projects' repos. `leadCheckouts(agentId)` says where a goal lead's checkouts are, as their work stands in their workspace (each repo, its folder and the branch it ships into), only to read, since the lead's at work in them: the cartography plugin maps them for what each goal's slice does to the architecture. `officeDir` is the office's own checkout, a real repo in the demo too (the cartography plugin maps it there, since the demo's repos are made up).
- **The whole office.** `snapshot` is the office as a browser gets it when it connects: projects, every agent with their recent terminal lines, boards, QA's reviews, the Ops stations' drafts and every plugin's state. It's a lot, so ask for it when it's needed (a call's answer), not on a timer, and only read it. `shipStatus` is the ship as the crew's `ship_status` tool tells it (`server/agents/shipStatus.ts`): who's on what and where their worktree is, the open pull requests, what needs the captain, and each closed goal's pull requests looked up on GitHub now. Number One reads both.
- **The captain's personal log.** `personalLog.entries()` is what the captain has jotted down to come back to ([personal log](personal-log.md)), and `personalLog.note(text, via)` jots a thought down for them, `via` whoever did (a crew member's name). Jot one down only when the captain asks. Number One does both.
- **The captain's goals.** `goals.start` starts a goal with a lead of its own at a free team station, or queues it when every station has one, saying where it came `from` (Number One's calls start theirs `from: 'a call'`); `goals.startQueued` starts a queued one at a station; `goals.message` passes a lead a word, as the captain's, or (`{ from }`) as a crew member's; on your API key it can come back `costly`, for the captain to say `how`. Do these only on the captain's word.
- **Read-only sessions.** `readOnlySession(run)` runs a read-only Claude Code session as the office's own crew do: only the built-in tools it's given (Read, Glob, Grep, WebSearch, WebFetch), all pre-approved, none of the captain's settings, hooks or MCP servers, and its answer (structured, with a schema). The retro's chief engineer reads and drafts in them. `shipSession(run)` is one with the run of the ship, as Number One's: from the office's planning folder (where `open_project` checks out a project's code), the agents' worktrees readable (its system prompt is told where), and the ship tools (`ship_status`, `open_project`) as `mcp__<plugin id>__…`, neither of which changes anything aboard. `drawModel({ question, title, dirs })` draws a model of how the code in `dirs` (checkouts, as `checkout` gives them) answers a question: a read-only session answers in the model tool's own shape, and the office checks and draws it as it does a lead's, with its page and picture. Cartography draws a kept diagram again with it. The demo's stand-in draws one model of the office's own code.
- **Talking.** A line in an agent's terminal (`print`), and a toast.

## In the browser

A plugin's `client.ts` default-exports a `ClientPlugin` (`client/src/plugins.ts`). The client finds every `plugins/*/client.ts` as it's built, and shows only those the office switched on. In the browser, a plugin reads its state with `pluginState(id)`, the office as the browser has it through `office` (read-only: its projects), and calls its own routes with `callPlugin(id, path, body)`, all from `plugin-api/client`. A plugin can add:

- **To the engineering station** (`engineering`), which the panel draws again whenever the plugin's state changes, or an agent on a brief does:
  - `top`: a block across the top of the overview, above its main block, in the order the plugins are switched on (the usage plugin's readout of your plan), or null for none;
  - `card`: a card on the overview, beside the others (the climber's, the retro's), with `go` to open one of the station's views from it;
  - `overview`: the overview's main block, with every card laid out in it (the scorecard puts them beside what moved); the first plugin's wins, and without one the cards stand on their own;
  - `readout`: what the overview's button on the side nav reads;
  - `views`: views of its own on the side nav, after the overview (the scorecard's Code and Office, the retro's Retro), each with a readout. A view gets `go`, to move to another view and scroll to what's in it;
  - `station`: what the chief engineer is busy with at his station in main engineering, when it's the plugin's work, or null: a status and one line, which his bubble says and his screen shows under the report card (the retro's `Retro: 2 drafts waiting`). The first plugin with something to say is heard; with none, he's keeping the ship running. It's drawn again as the plugin's state changes.

  The station's own views are the overview (the plugins' parts) and the **Ledger** (the report card as it stands, the open frictions, and **Digest them** for older sessions).
- **A word on each goal under way** (`goal`), which the core places on the goal's own surfaces:
  - `tag`: a readout on the goal's card in the goals list (`card`, under a label) or a tag on its lines in Comms (`line`). The core gives it its look (`goal-readout`, `goal-tag`) in the colour of its `--tone`. The goals list is drawn again as the plugin's state changes; Comms keeps lines from render to render, so a line's tag should keep itself up to date (the flow plugin's does, each minute and as its state changes).
  - `board`: a strip along the bottom of the goal board in its briefing room, with its height and a key: the board makes room for it, and draws it again when its key changes, as the plugin's state changes, and each minute while it's shown, so a time in it can count up.
- **A board on the MSD** (`msd`): what it draws beside the ship in main engineering while it's put up there, with `ui.showOnMsd({ plugin: id })`. It's drawn again as the plugin's state changes. The MSD shows the ledger's report card until something's put up, so with no plugin it's the report card and the traces picked at the master systems table.
- **A stat on the HUD** (`hud`): a pill in the HUD's top row, beside the office's own counts, wherever the captain is: `{ text, tone, title }`, with `tone` `warn` (gold) or `bad` (red) when it needs the captain's eye, or null for none just now. The HUD asks again as the plugin's state changes, and shows the plugins' stats in the order they're switched on (the usage plugin's `◔ session 9% · week 27%`). One whose `hud` throws is logged and left out.
- **Screens in a project's holodeck** (`hall`): given a project's id, the screens it hangs round that holodeck's wall, either side of the entrance, each a hologram you walk up to (`world/hallScreens.ts`). A screen has a `key`, a `title` (aiming at it reads *Look at …*), a `version`, and `draw(ctx, w, h)` on a 1280 × 800 canvas, which may be async. It's drawn again only when its `version` changes, at most as often as the board is. `closeUp(ui)` is what E on it opens. They're asked for again whenever the plugin's state changes. A hall has room for `HALL_SCREENS` (6) in all, given out in the order `FOCUS_PLUGINS` lists the plugins. No plugin hangs one today: the cartography plugin's views moved to a space of its own (`ship`, below), since six screens round the wall crowded the team pods.
- **What it does from the start** (`start`): called once with the app (`{ ui }`), when the office's first snapshot says the plugin is on, for what it does outside any panel: Number One's toast when a reply lands (with **Read it**, a toast action that opens its panel), and letting go of the call's mic when the office ends the call. It returns the parts that run from then on: `keydown`, a key pressed while the captain walks the ship (not typing, nor in a panel that hides the view), heard before the core's own keys, true when it used it. Use only keys of the plugin's own, and check `ui.panels.isOpen` (Number One's <kbd>1</kbd> does nothing with a panel open). A key can open a panel of the plugin's own with `ui.panels.open({ title, body })`, as the captain's log's <kbd>J</kbd> does. And `answered`, the captain answered a goal's lead from Comms (approved or declined a tool, picked an option, replied, closed the goal), with the lead as they stood when they did: heard only after they've decided. The chief of staff says what it thought of that turn.
- **Its part of the station's screen** (`screen`): given a page a goal's lead put up, open up close (`ScreenView`: the `ui`, the lead's id, the artifact, its live page's `frame`, and whether the goal's still `live`), what it adds round it, or nothing: a `head` beside its title, a `foot` under it, `heard` for each message posted to the window while it's open (the page runs sandboxed, so it talks by `postMessage`: check it's from `frame`), and `end`. When the lead shows the same id again, the new version's `screen` gets the plugin's part for the old one as `before`, which the screen doesn't end: the plugin carries over what should outlast it and ends the rest. The briefings plugin's narrator is one.
- **Keys in the legend** (`legend`): `{ key, label }`s added to the controls listed on the splash screen and along the bottom of the view (`1 Number One`).
- **A part of the ship** (`ship`): built with the rest each time the World builds the ship (as projects come and go), and disposed before the next. Its `ShipHost` lends a deck's seat marker by name (`seat('command', 'ready-room-guest')`, undefined when the deck has none), `mount` to put something on a deck (drawn and culled with it, taken off on the next build), `collide` for a box the player can't walk into, `hall(projectId)` to stand things in a project's training hall (`mount`, placed in the hall's own frame from `world/hallLayout.ts` and culled with it, and `toWorld` for its points in world coordinates), `space(label)` for a place of its own far out beyond the rest of the ship (`world/layout.ts` `SPACE`), a region of its own (`world/regions.ts`) drawn only while you're in it, which it fills, sky and all, and sends the captain to and from (`ui.dive(place)`, a rush into what you looked at, or `ui.goTo`), with `label` for the HUD's place while you're there, and `interactive` to make something usable with <kbd>E</kbd>, from as far as its `reach` (its hint, and what it does with the app: `use` is handed the `Ui`, since the World that builds the ship has none of its own, which is why `world/builder.ts` imports the `Ui` type). The part follows its own state (subscribing as it's built, and unsubscribing in `dispose`), and `update` runs each frame with the camera. What a part asks of its host is held until its `ship` returns: one that throws is logged and left out with all it asked for (`shipParts`), so the ship is built without it. Parts are built only as the World builds the ship, so a plugin the office switches on while a browser stays connected (a restart with a different `FOCUS_PLUGINS`) starts at once but stands in the ship only from the next build, and one switched off isn't stopped until the page reloads. Number One's figure is one: a chair, the character and their PADD at the ready room's guest seat. The cartography plugin's stellar cartography screens and architecture space are another: a hologram on the wall of each holodeck it's on for, and the space it takes you to. What a part asks of its host after its `ship` returns (making a view usable as it puts it up, say) is done at once; a space it made is dropped with it if it throws.

A plugin's `client.ts` is loaded whether it's switched on or not (the client finds every one as it's built), so it must do nothing as it loads: no listeners, no timers. Anything that runs goes in `start` or `ship`, which only run for plugins switched on. Its CSS (imported from its `client.ts`) is always bundled too, so give its classes names of its own (`number-one-call`).

## Writing one

```
plugins/<id>/
  server.ts     default-exports the FocusPlugin
  client.ts     optional: default-exports the ClientPlugin
  <id>.css      optional: its styles, imported by client.ts (bundled whether it's on or not, so its own class names)
  shared.ts     types and constants both halves use (its state's type)
  README.md     what it does, and where it lives
  *.test.ts     its tests (vitest finds plugins/**/*.test.ts)
```

### The plugin API

A plugin reaches the office only through `plugin-api/`, the core's one published surface for plugins:

- `plugin-api/shared.ts`: the office's types and pure values both halves use (`Agent`, `Project`, `LedgerEvent`, `ModelKind`, `SignIn`, the recorded flows…), the ledger read as the office reads it (`reportCard`, `frictionGroups`, a line of it as the ledger review shows it with `ledgerRow`, and lines by day with `byDay`), and a time of day as the office writes one (`clock`);
- `plugin-api/server.ts`: the contract a `server.ts` implements (`FocusPlugin`, `PluginHost`…) the helpers it shares with the core (`errorMessage`, `run`, `sleep`), the environment the office's Claude Code sessions run in, for a plugin that starts one through the Agent SDK itself (`agentEnv`: `agentEnv(false)` signs in with your plan, as the usage plugin's reading of `/usage` does), reading the journals (`LentJournals`, `JournalEntry`, `ReviewEntry`, `SliceFact`, `Stamped`, `evolveReview`, `evolveSlice`, `factLine`), reading an agent (`hasLeadWork`, `goalRecord`) and a session's transcript (`transcriptLines`, `blocks`, `messageFrom`…), QA's latest catch rate (`latestQaCatch`), and for its scripts, which run without a host, its folder (`pluginDataDir`), the office's ledger (`officeLedger`), its agents' transcripts (`officeTranscript`) and its clones of repos (`officeMirror`), with everything in `shared.ts`;
- `plugin-api/client.ts`: the contract a `client.ts` implements (`ClientPlugin`, `HudStat`…), `pluginState`, `onPluginState`, `office` (its projects, its agents and the ledger's report card), `callPlugin` the station's UI kit (`h`, `busy`, `timeAgo`, `markdownHtml`, `frictionBars`, `Ui`) and the LCARS kit for what it draws on a canvas (`LCARS`, `LCARS_FONT`, `LCARS_STATUS`, `fitText`, `Box`), with everything in `shared.ts`;
- `plugin-api/layout.ts`: where the ship's spaces and holodeck halls are (`SPACE`, `around`), plain geometry that loads without the browser, and also exported from `client.ts` with the ship kit (`ShipHost`, `ShipPart`, `PluginSpace`, `Hologram`, `hover`, `canvasTexture`, `makeCanvas`);
- `plugin-api/testing.ts`, for its tests only: `office()`, a pretend office its tests can switch it on in, `until`, `OFFICE_DIR`, and `checkRestart` and `checkAtOnce`, the office's [two rules for state](invariants.md).

Whatever the API doesn't re-export, the core can change without a plugin noticing. When a plugin needs more of the office, the API grows: what the office does for a plugin (files, checkouts, GitHub, sessions) goes on the host, so the core decides what a plugin can do and a test can lend it a fake; a type or a pure helper is re-exported. For another plugin, see [plugins that need each other](#plugins-that-need-each-other): it reaches what that plugin provides through the host, and imports only that plugin's `api.ts`.

`plugin-api/boundary.test.ts` holds the repo to it, resolving every import as TypeScript does: a plugin imports only its own files, `plugin-api/` (`testing.ts` from tests alone), npm packages and another plugin's `api.ts`, and the core never imports a plugin. Every plugin is held to it, a new one from the start: an import past the API fails the suite, naming the file, the line and why.

Typecheck, lint (no non-null assertions outside tests, as in `server/`), the scorecard's fence and CRAP cover `plugins/` like the rest.

A plugin outside the office's folder can be switched on by path, but for now it still imports `plugin-api/` by relative path, and its `client.ts` isn't found (only `plugins/` inside the checkout is). Plugins in repos of their own need the API published as a package first.

Both sides stand on their own. The core needs no plugin: with `plugins/` deleted, it typechecks, its tests pass (they load plugins of their own making, never the office's by name), the client builds and the demo office runs, with the engineering station's own Overview and Ledger. And a plugin needs nothing of the core but the API: each of the office's plugins typechecks in a folder of its own outside the checkout, against `plugin-api/` emitted as declarations (`tsc --declaration --emitDeclarationOnly`), with no source of the core beside it. Those declarations still carry the core's own types that the API's reach (a published package would bundle only the API's, with API Extractor or the like), so it's `boundary.test.ts`, not the build, that keeps a plugin from importing past the API.

## Where it lives

- `plugin-api/`: what a plugin may import of the office, and `boundary.ts`, the line its test holds the repo to.
- `server/plugins/contract.ts`: what a plugin is, what it adds and what the office lends it.
- `server/plugins/registry.ts`: `Plugins`, the core's one way to the plugins switched on (briefs, states, routes, hooks). The manager's core holds it (`core.plugins`), and the office reaches it through `office.agents.plugins`.
- `server/plugins/load.ts`: finding and loading what `FOCUS_PLUGINS` names (`all` too).
- `server/agents/manager/pluginHost.ts`: the `PluginHost` the manager lends each plugin, and its state slot.
- `server/plugins/migrate.ts`: state saved before parts of the office became plugins, moved into their slots as `state.json` is read (or dropped, like a goal's flow, which the flow plugin works out again).
- `client/src/plugins.ts`: the plugins' parts in the browser, `goalTags` and `goalStrips`, which the goals list, Comms and the goal board place, `hudStats`, the HUD's pills, and `stationSays`, what the engineer at the engineering station says. `main.ts` starts each plugin once and asks their `keydown`s before its own keys; the World builds their parts of the ship (`world/shipParts.ts`) after the decks.
- `server/agents/shipStatus.ts`: the ship's status lent as `host.shipStatus` (the office builds it in `index.ts`, with GitHub and the agents' worktrees).
